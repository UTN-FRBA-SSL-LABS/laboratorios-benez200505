## Introducción

Tenés que implementar el backend de un carrito de compras simple. El código ya está escrito en `src/carrito.c`, pero **tiene bugs**. Tu trabajo es escribir tests que los descubran y luego corregirlos.

El módulo expone estas funciones:

```c
void carrito_init(Carrito *c);
int  carrito_agregar(Carrito *c, Producto p);  /* 1=ok, 0=lleno */
int  carrito_contar(Carrito *c);
int  carrito_total(Carrito *c);
int  carrito_descuento(int total, int porcentaje);
```

Y estas estructuras (en `src/carrito.h`):

```c
typedef struct {
    char nombre[32];
    int  precio;    /* precio unitario en pesos */
    int  cantidad;
} Producto;

typedef struct {
    Producto items[MAX_ITEMS];  /* MAX_ITEMS = 4 */
    int      cantidad;
} Carrito;
```

## Parte 2: El framework de testing

Antes de seguir, abrí `tests/minunit/minunit.h`. Es el framework que usamos — apenas 60 líneas de C.

Los macros principales son:

```c
ASSERT_IGUAL(esperado, obtenido)  /* verifica que dos enteros sean iguales */
ASSERT_VERDADERO(condicion)       /* verifica que la condicion sea verdadera */
RESUMEN()                         /* imprime cuantos tests pasaron/fallaron */
```

Cuando todos los tests pasan, el programa termina con **exit code 0**. Si alguno falla, termina con **exit code 1**.

**P3** — ¿Qué hace `carrito_init` y por qué es importante llamarla antes de usar el carrito?

> R:Inicializa la cantidad de elementos del carrito en 0. Es crucial llamarla porque en C las variables locales no se limpian solas; si no lo hacemos, la variable cantidad podría arrancar con "basura" y romper la lógica al agregar o contar productos.

## Preguntas de reflexión

**P11** — ¿Qué diferencia hay entre un test unitario y uno de integración? ¿Cuál de los dos detectó primero el bug de `carrito_total`?

> R:Un test unitario prueba una función o componente específico de forma completamente aislada. En cambio, un test de integración prueba cómo interactúan varias funciones o partes del programa trabajando juntas. El bug de carrito_total lo detectó primero el test unitario (específicamente la prueba test_total_con_cantidad).

**P12** — El bug de capacidad en `carrito_agregar` causa un **buffer overflow**: se escribe más allá del array. ¿Por qué esto es peligroso en C pero no ocurriría en un lenguaje como Python o Java?

> R:Es peligroso en C porque el lenguaje asume que el programador controla la memoria y no verifica automáticamente los límites de los arreglos. Escribir fuera del límite sobrescribe memoria adyacente, causando comportamientos impredecibles, cuelgues o graves vulnerabilidades de seguridad. En Python o Java, el entorno de ejecución chequea los límites constantemente; si te pasás, el programa lanza un error controlado (una excepción como IndexOutOfBoundsException) en lugar de corromper la memoria.

**P13** — En este laboratorio encontraste los bugs escribiendo tests. ¿Qué tiene de mejor este enfoque frente a mirar el código directamente?

> R:Los tests son verificaciones automáticas, objetivas y repetibles. Inspeccionar el código a ojo es propenso a errores humanos (el cerebro suele "leer lo que debería decir" y no lo que realmente dice). Además, los tests te protegen contra regresiones: si mañana alguien modifica el archivo y vuelve a romper la suma, el test va a fallar al instante y avisarte antes de que el código llegue a producción.

**P14** — El test `test_total_precio_unitario` (cantidad = 1) **pasó** a pesar del bug, mientras que `test_total_con_cantidad` (cantidad = 2) **falló**. ¿Por qué el primer test no detectó el bug?

> R:Porque el código defectuoso sumaba el precio base sin multiplicarlo por la cantidad (total += precio). Como en el primer test la cantidad era exactamente 1, matemáticamente el valor de precio era igual a precio * 1. El resultado dio bien por pura casualidad aritmética, camuflando el bug.

```

```

```

```
